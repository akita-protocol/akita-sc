# Algorand Access-list resource audit

Status: whole-repository source audit with post-build carrier reconciliation, 2026-07-16

This document maps the ledger resources that can be touched by every production contract family and every public ABI method variant in this repository. It is a design input for the SDK Access-list preparer; it is not a recommendation to hard-code one static list per method. A large fraction of the actual IDs and box keys are state-derived, and several methods have branch-dependent or data-dependent call graphs. The reliable implementation is therefore simulation-driven, with the static map below used to seed resources, size carriers, identify protocol-impossible calls, and build regression tests.

## Scope and audit result

- Audited all 94 `.algo.ts` sources under `projects/akita-sc/smart_contracts` and `projects/akita-plugin`.
- The initial resource-path reconciliation cross-checked the pre-carrier-expansion/pre-cleanup snapshot of 93 ARC-56 artifacts and 889 exposed ARC-4 method entries, including inherited methods, sub-gates, ARC-58 plugins, sunset contracts, and mocks/stubs. Those numbers describe the audit input, not the current post-build ABI method total.
- The initial source classification was 73 production application classes/839 inherited ABI methods; two non-deployed support/type contracts; 14 mock/test applications; two LogicSigs; and one empty plugin template base.
- **Current carrier invariant:** after the mandated root build, 88 of the 89 generated ARC-56 application specs resolve the public ABI method `opUp()void`. The sole exception is `AbstractedAccount`: adding the route produced an 8,195-byte approval program, three bytes beyond the 8,192-byte program/factory limit, so that route was removed. The SDK registers its existing readonly `arc58_getAdmin()address` method as the wallet's safe zero-resource carrier instead. The other direct-`Contract` classes, ARC-58 plugins, support applications, sunset applications, and mocks expose `opUp`. These carrier routes add no ledger-resource branch, so the resource-path conclusions from the original snapshot are unchanged.
- The cleaned tree now contains 89 compiler-owned ARC-56 artifacts with no duplicate contract names, and every retained approval is AVM v11, above the AVM v9 group-resource-sharing threshold.
- None of the current ARC-56 methods has an ARC-4 reference argument type (`account`, `asset`, or `application`). Current source-level `Account`, `Asset`, and `Application` values are encoded as `address` or `uint64`. This removes a current ABI-index rewrite problem, but the SDK must retain a future guard for external/custom calls.
- The only production code that intentionally reads the old top-level reference-array slots is `HaystackRouterPlugin`; its exception is documented below.
- Static per-method resource tables cannot make the SDK reliable. DAO registries, gate definitions, wallet boxes/globals, proposal actions, revenue splits, marketplace state, opt-in state, NFD state, hook registries, and winner/seller/referrer state all change the actual graph.
- Some accepted parameter/state variants are larger than the consensus Access capacity of one atomic group. Those paths require contract caps, cursor/batch methods, or SDK chunking where atomicity is not required.

## Resource notation

| Notation            | Meaning                                             | Encoded Access implications                                                                                                                                                                                                                                 |
| ------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `P(app)`            | Application/global-state/program resource for `app` | One primitive entry unless it is the called app for that transaction.                                                                                                                                                                                       |
| `A(address)`        | Account record                                      | One primitive entry unless it is that transaction's sender. Under Access, an app reference does **not** implicitly provide the app account; simulation may separately report `A(app.address)`, including the called app's account.                          |
| `S(asset)`          | Asset parameters                                    | One primitive entry.                                                                                                                                                                                                                                        |
| `H(address, asset)` | Asset holding                                       | Composite entry plus earlier `A(address)` and `S(asset)` entries in the **same transaction's** Access list. Sender can use address index zero. Usually three entries; fewer only when a dependency is already present locally.                              |
| `L(address, app)`   | Application local state                             | Composite entry plus earlier `A(address)` and `P(app)` in the same Access list. AVM/consensus v41 does not support a zero current-app index for a non-sender local reference, so that composite may need to be placed on a carrier calling a different app. |
| `B(app, key)`       | Box resource                                        | One composite entry. If `app` is foreign to the carrier, an earlier `P(app)` is also required in that carrier's Access list.                                                                                                                                |
| `Q(n)`              | Box I/O quota entries                               | `ceil(n / 2,048)` box/empty entries under consensus v41. A named box reference counts as one of these entries.                                                                                                                                              |
| `E(k)`              | `k` empty Access entries                            | Adds `k * 2,048` bytes of group box I/O quota. Empty entries also authorize unnamed boxes in apps created in the same group.                                                                                                                                |
| `-> method`         | Transitive inner ABI call                           | The callee's full resource path is inherited by the top-level group; inner app calls cannot supply their own Access list.                                                                                                                                   |

Box names in this document use the source `BoxMap` name and logical key, for example `B(Rewards, userAllocations[id,user,asset])`. The SDK must use the exact ARC-4/key-prefix bytes generated by the relevant client/state accessor.

## Consensus rules that drive the implementation

1. An application transaction can encode at most 16 Access entries. The old `Accounts`, `ForeignApps`, `ForeignAssets`, and `Boxes` arrays must all be empty when `Access` is non-empty.
2. A group has at most 16 transactions. Only application-call transactions can carry Access entries. A payment or asset-transfer argument consumes a group slot without adding Access capacity.
3. Resources are shared by AVM v9+ programs across the atomic group. A group may mix a legacy-array app call and Access-bearing app calls.
4. Composite dependencies are local to the Access list that encodes the composite. A foreign box on a generic carrier generally costs `P(owner) + B(owner,key)` in that carrier even if `P(owner)` exists in another transaction.
5. Each box/empty entry contributes 2,048 bytes of group I/O quota. A 32 KiB box needs 16 entries; an 8 KiB boxed program needs four; a 3,151-byte subscription description needs two.
6. Boxes of an app created earlier in the group can be authorized with empty references because their ID and names cannot be predicted. This removes the naming/read problem only. The full write quota still applies. Go-algorand tracks the complete create size as dirty bytes, so a newly created 32 KiB box still needs 16 empty refs.
7. Simulation's group resource tracker counts unused group slots as potential empty app-call carriers. It can therefore report more resources than the app calls currently present can encode. The SDK must add carriers rather than treating such a report as an unrecoverable packing error.
8. Created app/asset resources become available within the group, but inner transactions cannot set Access. Their resources must be on top-level app calls.
9. Access solves ledger-resource availability, not opcode budget or fees. Both must be sized.

The practical group capacity is not simply 256 entries. If there are `N` non-app transactions, the absolute upper bound is `16 * (16 - N)`, before foreign composite dependencies and legacy-only app calls reduce it further.

## Required SDK discovery and packing model

Every SDK terminal that builds, sends, simulates, or hands off a group must use one central preparer:

1. Build the intended group without AlgoKit's legacy resource population.
2. Preserve explicit transaction arguments and seed any caller-supplied account/app/asset/box resources.
3. Simulate with `allowUnnamedResources: true`, permissive signatures/signers, and a large `extraOpcodeBudget`. Without extra opcode budget, a deep path can fail before all resources are reported.
4. Merge transaction-level and group-level unnamed resources, including `asset-holdings`, `app-locals`, and `extra-box-refs`.
5. Prefer placing `B(app,key)` on a call to `app`; place holdings/locals where their dependencies have the smallest incremental encoded cost.
6. Deduplicate semantic resources, but never deduplicate the repeated empty entries required for box quota or newly created unnamed boxes.
7. Add the minimum number of safe app-call carriers necessary for both Access capacity and pooled opcode budget. For 88 current generated applications, the SDK can call `opUp()void` on the target itself or another carrier-capable Akita app. For `AbstractedAccount`, use its exact readonly `arc58_getAdmin()address` selector. Carrier registration is scoped to the algod client/network and exact ARC-56 signature; an external third-party or pre-upgrade plugin is never called speculatively.
8. Clear all four legacy arrays on converted transactions. Preserve the Haystack router transaction as legacy; use a separate Access-bearing `HaystackRouterPlugin.opUp()` call or another safe Akita carrier. Also retain legacy arrays for any future/custom ARC-4 call that actually uses indexed `account`, `asset`, or `application` reference arguments.
9. Fail before signing with a precise protocol-capacity message when no legal group can hold the call.
10. Recalculate byte-based outer transaction fees after Access packing, then let AlgoKit add simulated inner-transaction fee deficits within each call's `maxFee`.
11. Run a final strict validation simulation. Rebuild, merge newly discovered resources, and retry when strict validation exposes a branch that the discovery pass did not reach.

“Always works” can only mean “all paths that fit consensus, against the state simulated for submission.” It cannot cover an over-cap atomic request or a concurrent state change without chunking/retry semantics.

The accepted `weightsListCount = 15` creation variants are protocol-impossible as one group. The non-PrizeBox variant has an absolute 224-entry ceiling after pay+axfer, and the new boxes alone need 240. The PrizeBox variant can expose at most 240 entries across its app calls, but the boxes consume all of them before boxed program/DAO/PrizeBox/ticket resources. Creation must be split from weight-box initialization, boxes must be smaller, or the contract must impose a lower proven cap.

`AbstractedAccount` deliberately has no `opUp` ABI route. The attempted route compiled to 8,195 bytes, beyond both the 8,192-byte approval-program limit and the factory's 8,192-byte boxed-program capacity. Its readonly, zero-argument `arc58_getAdmin()address` route touches only wallet globals, so the SDK registers that exact selector as the wallet's safe Access/opcode carrier. Plugin groups may instead use `opUp` on a current plugin application; the SDK must not assume that a legacy deployed plugin exposes it. Wallet mutation and bulk-read arrays remain caller-controlled and still need caps/chunking when the simulated full group exceeds consensus. Their resources cannot be predicted from only `opUpCount`; they depend on the actual plugin transactions, wallet key, named escrow, lease, allowances, and downstream state.

## Haystack legacy-array exception

`HaystackRouterPlugin.assertRouterCall`/`getAccountRef` compile to `gtxnsas Accounts` and `gtxnsas Assets`. The Haystack router call supplies indices in application arguments, and the plugin authenticates the exact account/asset at those old array positions.

Consequences:

- Do not convert that external router transaction to Access unless its application arguments and all indices are intentionally re-encoded to the Access layout. Access leaves `Accounts` and `Assets` empty.
- Preserve the router's legacy arrays **and their order**.
- A group may still put all additional resources on other Access-bearing app calls. Mixed legacy/Access transactions are legal and AVM v9+ resource sharing makes them available to the plugin path.
- If every existing business app call in the group must preserve legacy indices, add a separate Access-bearing `HaystackRouterPlugin.opUp()` transaction to the same app or call `opUp()` on another carrier-capable Akita application. Keep only the external router transaction on legacy arrays.
- The NFD contracts' `itxn_field Applications` usage is not a top-level legacy-array exception. Inner calls cannot carry Access and inherit top-level group resources.
- No other production approval reads `NumAccounts`, `NumAssets`, `NumApplications`, `Accounts`, `Assets`, `Applications`, or `Boxes` slots for semantic indexing.

## Explicit opcode-budget paths

The following methods explicitly call `ensureBudget` and therefore require fee/budget treatment in addition to Access:

- `Gate.evaluate`, reached by `check` and `mustCheck`.
- `MetaMerkles.verify` and all methods/sub-gates that call it.
- `Auction.findWinner`, `refundMBR`, and `clearWeightsBoxes`.
- `Raffle.findWinner` and `refundMBR`.

Many other methods have dynamic loops without explicit `ensureBudget`: Poll bulk deletion, Staking list operations, StakingPool entry/disbursement loops, Subscriptions list/pass/trigger loops, Rewards allocation/claim/reclaim loops, DAO action/vote loops, AbstractedAccount plugin/allowance/asset/getter loops, RevenueManager assets-by-splits, PluginDex hooks, pay/opt-in/ASA arrays, and Sunset cleanup arrays.

The discovery simulation must use a large `extraOpcodeBudget`; then the preparer must add enough application calls to satisfy both:

```text
carrierCount >= max(
  ceil(encodedAccessEntries / 16),
  ceil(requiredPooledOpcodeBudget / perAppCallBudget)
)
```

The exact formula must account for existing app calls, non-app group slots, foreign composite dependency overhead, and inner fee coverage.

## Protocol-impossible atomic cases and required caps

| Path                                                        | Why automatic Access cannot make it work                                                                                                                        | Required product/contract response                                                                                                                             |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auction/Raffle child init with too many 32 KiB weight boxes | 16 entries per box. Raffle accepts 15; Auction has no upper bound. Creation groups also contain payment/asset/PrizeBox transactions and many non-box resources. | Create child first and initialize boxes over cursorized calls; shrink/chunk boxes; or impose a proven lower cap. Add Auction `<= 15` logical bound regardless. |
| `Raffle.clearWeightsBoxes` at 15                            | Needs 240 quota entries plus creator account. It theoretically fits only in a nearly full 16-app-call group.                                                    | SDK must construct the full carrier group; add a cursorized `clearWeightsBoxes(iterationAmount)` for operational margin.                                       |
| `Rewards.claimRewards` with many unique claims/assets       | Roughly two boxes plus asset/holding dependencies per item can exceed group capacity while ABI args remain valid.                                               | SDK chunk claims; expose/return partial results explicitly if needed.                                                                                          |
| Gate register/check/get of large filter list                | Each filter adds a sub-gate app and arbitrary transitive graph; no safe filter cap.                                                                             | Cap filters/resources or implement cursorized gate evaluation/registration.                                                                                    |
| RevenueManager allocation of many assets across ten splits  | Assets x splits x opt-in fallbacks expands faster than the group.                                                                                               | SDK simulation-sized asset batches; contract already has phase/counter semantics.                                                                              |
| DAO proposal execution                                      | Stored action list can expand into many wallet boxes/plugins/allowances/executions/apps.                                                                        | Cap proposal action complexity or execute with an action cursor and explicit atomicity semantics.                                                              |
| PluginDex hooks                                             | Stored unbounded arbitrary hooks have unknown transitive resources. Its `PluginDex.opUp()` carrier helps only while the graph remains within group capacity.    | Cap hooks per execution or cursorize hook execution; reject over-cap executions before signing.                                                                |
| `AbstractedAccount` direct bulk getters                     | The readonly admin getter supplies safe in-wallet carriers, but one getter can still name more wallet boxes/quota than the entire 16-transaction group can encode. | Build the full simulator-sized carrier group; page each list or reject before signing only when that group exceeds consensus capacity.                         |
| Other bulk readonly/mutation lists                          | Subscriptions, Staking, EscrowFactory and Sunset can name more boxes than a group.                                                                              | Page readonly methods; chunk independent mutations; reject atomic batches that cannot be split.                                                                |

No SDK should silently truncate an `opUpCount`, resource list, claim list, or cleanup list. It must either build the full legal group, split with documented semantics, or fail before signing with the exact limiting resource count.

## Artifact and SDK hazards found during the inventory

These issues are adjacent to Access correctness because they can prevent a variant from being encoded or can generate the wrong client before simulation:

1. `projects/akita-sdk/src/gates/index.ts` imports `NFDRootAppSpec` from `../generated/NFDGateClient` instead of `../generated/NFDRootGateClient`.
2. The same file configures `subscription_streak.registerShape` as `SubscriptionGateRegistryInfo`; the current artifact exposes `SubscriptionStreakGateRegistryInfo`.
3. Artifact cleanup is complete: the stale `gates/sub-gates/nfd-root/NFDGate`, plugin-side `AkitaSocialImpact`, source-less `DAOStub`, and duplicate mock-beacon artifact sets were deleted.
4. The retained tree has 89 compiler-owned ARC-56 specs and no duplicate contract names, so recursive SDK generation is deterministic. Keep generation on the clean root-build output and make it reject future duplicate contract names.
5. The installed AlgoKit Utils resource populator still writes the old arrays and applies the old combined limit of eight. It also omits `extraOpcodeBudget` from its composer analysis simulation. The SDK must own both behaviors until upstream support is verified.

## Completion criteria

The migration is complete only when:

- every SDK send/build/prepare/handoff terminal flows through the central Access preparer;
- the root build and generated-client checks preserve the invariant that 88 of 89 generated application specs expose `opUp()void`, with `AbstractedAccount` as the sole size-constrained exception;
- wallet and wallet-plugin groups use a network-scoped exact-signature carrier (`arc58_getAdmin()address` for the wallet or `opUp()void` for a current plugin), while only consensus-overflowing direct reads page or reject before signing;
- every within-consensus branch above succeeds without a manual `opUpCount` adjustment;
- over-cap branches are chunked/cursorized or rejected deterministically before signing;
- Haystack's router arrays retain exact legacy ordering while the rest of its group uses Access;
- contract/SDK integration tests assert Access on-chain, not merely that simulation passed;
- and the public manual `opUpCount` workaround is removed only after opcode and carrier sizing are automatic.
