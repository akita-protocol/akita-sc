# Twenty-two primitives cover all on-chain finance

A unified finance kernel on Algorand needs **22 primitives** to host every major product family in this survey, and only **seven of them belong in the kernel app itself**: a session guard, a delta ledger, measured credit, a custody guard for flash rekeys, a two-class settle check, a lien registry with one controller per margin account, and a forced-action right for liquidation. Everything else (curves, oracles, interest indexes, signed orders, vault shares, outcome tokens, epochs, sorted indexes) is a shared service or a module on top. The model has strong precedents. Uniswap v4 and Balancer v3 keep signed per-asset deltas and require them flat at the end, and Euler's Ethereum Vault Connector (EVC) defers per-account health checks to the end of a batch. The first user challenge has a clean answer. No production system stores a negative balance. Each one stores a signed ledger entry and moves real tokens only when someone pays, so the AVM abort on underflow becomes the enforcement at settle, not a blocker. The second challenge is correct and serious. Under the current ARC-58 wallet code, the admin can rekey the account, update the app, remove any plugin, change the admin, and reclaim a locked escrow in any later group. So **no plugin-level lien survives the owner**, and "the whole wallet backs margin" is unsafe as designed. The fix: positions stay in the wallet only while they carry no debt, and margin sits in an escrow that only the kernel can release. Market context sets the order of work. Algorand DeFi TVL is about **$30.8M** and 30-day DEX volume about **$11.9M** (DefiLlama, 4 Nov 2026). No perps venue is live, and no native Chainlink or Pyth feed is confirmed. Ship the "flatness kernel" (spot, routing, flash loans, vaults) first. Gate the "solvency kernel" (lending, CDPs, perps) on an oracle module and on a wallet-contract decision.

## The kernel model, in the terms this report uses

The report uses one term for each thing. The table defines them once.

| Term | Meaning in this report |
|---|---|
| **Atomic group** | Up to 16 top-level Algorand transactions that all succeed or all fail ([Algorand atomic groups](https://dev.algorand.co/concepts/transactions/atomic-txn-groups/)). |
| **Kernel** | One immutable app that opens a session, keeps the delta ledger, and runs settle. |
| **Module** | A separate app that does one financial action (swap, borrow, liquidate) inside a session. |
| **Account** | Any Algorand address the kernel tracks: a pool escrow, a user's ARC-58 wallet, a margin escrow, a protocol reserve. |
| **Escrow** | A separate Algorand account rekeyed to an app, so the app signs for it with inner transactions. |
| **Flash rekey** | An escrow is rekeyed to a module for part of the group and must be rekeyed back before the group ends. |
| **Session** | The span from the kernel `open` call to the kernel `settle` call in one group. |
| **Delta** | A ledger entry per (account, asset) that records what the account owes or is owed inside the session. It is not a balance. |
| **Settle** | The last kernel call. It checks every touched account and reverts the group if any check fails. |
| **Touched account** | An account that a module changed during the session. |
| **Pool account** | An account that must end the session flat or with its invariant preserved. |
| **Margin account** | An account that may end the session with debt, if its health check passes. |
| **Controller** | The single module that owns the health rule for a margin account and alone can release it (the Euler EVC term). |
| **Lien** | A rule that stops the owner from moving value or authority out of a margin account while debt exists. |
| **MBR** | Minimum balance requirement: ALGO an account must keep for its assets, apps, and boxes. |

Three patterns stand out in this table. First, **order flow, not pool design, decides spot volume**. Solana prop AMMs took about 71% of DEX volume through aggregators alone, and leadership moved from HumidiFi (over 68%) to BisonFi (over 34%) within about a month ([Step Data](https://stepdata.substack.com/p/prop-amms-on-solana-bisonfi-ends)). A kernel venue must be easy to quote before it is clever. Second, **lending and perps converge on one account model**. Hyperliquid shipped portfolio margin in stages, with beta from 25 Jun 2026 ([supa.is](https://supa.is/article/hyperliquid-portfolio-margin-beta-limits-increased-2026)). Fluid makes LP positions into collateral ([DeFi Saver](https://help.defisaver.com/protocols/fluid/vault-protocol)). Both need one health check over many module positions, and that is the settle call. Third, **most "order types" are one primitive**. Limit, stop, DCA slices, RFQ, and Dutch auctions all reduce to "verify a signed order, compute the amount allowed now, move funds, record the fill". Akita's ARC-58 execution keys and allowances already cover the authorization half.

The ranking holds one design lesson. **Pool accounts and margin accounts need different end checks.** Uniswap v4 and Balancer v3 run no health check at the end. They only require every delta to be zero. Health checks at the end come from the EVC. A kernel that mixes the two into one "all deltas zero" rule cannot host lending, because a borrower legitimately ends a session with debt in asset X backed by collateral in asset Y.

## Temporary debts live in a ledger, so uint64 never needs to go negative

The user's first challenge is correct on the facts. The AVM `-` opcode is "A minus B. Fail if B > A", and the byte-array math `b-` also fails on underflow ([AVM opcodes](https://dev.algorand.co/reference/algorand-teal/opcodes/)). The AVM has no signed integer type. The challenge does not break the kernel, because **no system in the survey stores a negative token balance**. Each one stores a signed ledger entry and keeps real balances non-negative.

### Four precedents use the same idea

Uniswap v4 keeps one signed `int256` per (caller, currency) in EIP-1153 transient storage. `take` applies a negative delta and transfers tokens out. `settle` applies a positive delta equal to the measured balance increase since `sync`. `unlock` reverts with `CurrencyNotSettled` unless a global nonzero-delta counter is zero ([PoolManager.sol](https://github.com/Uniswap/v4-core/blob/main/src/PoolManager.sol); [CurrencyDelta.sol](https://github.com/Uniswap/v4-core/blob/main/src/libraries/CurrencyDelta.sol)). Balancer v3 uses the same design with the opposite sign. Its `settle` computes credit as live balance minus booked reserves, capped by a caller hint ([Vault.sol](https://github.com/balancer/balancer-v3-monorepo/blob/main/pkg/vault/contracts/Vault.sol)). Euler's EVC does not net deltas at all. It defers predicates: vaults register "check this account" in a set capped at 10 entries, and the account's single controller runs the health check when the outermost call ends ([EVC whitepaper](https://github.com/euler-xyz/ethereum-vault-connector/blob/master/docs/whitepaper.md)). Sui goes further. A flash-loan receipt is a "hot potato" struct with no abilities, so the VM refuses to finish the transaction until the receipt is consumed ([Move Book](https://move-book.com/programmability/hot-potato-pattern); [Trail of Bits](https://blog.trailofbits.com/2025/09/10/how-sui-move-rethinks-flash-loan-security/)).

Algorand sits between Solana and Sui. It has no linear types, but an app can read later transactions in its group with `gtxn` and so prove at `open` that a closing call exists. The repo already ships the AVM version of the ledger idea. `plugin-dex/math.ts` defines `SignedDelta = { mag: uint64; neg: boolean }`, with the rule that `neg` is false at zero and raw uint64 subtraction is banned on delta paths. `applySigned` asserts `value >= delta.mag` before it subtracts ([local math.ts](../math.ts)). The Vault's `bookDelta` classifies measured pool deltas and bounds any loss to the liquid reserve ([local contract.algo.ts](../contract.algo.ts)).

### The underflow abort is the enforcement, not the enemy

A real ASA or ALGO transfer above the sender's balance fails, and any failure reverts the whole group. So the kernel never needs a negative balance. It needs two rules. Inside the session, no code computes `balance - owed`; it only adds to ledger columns. At settle, one explicit assert per pool account (`credit >= debit`, or credit equal to debit for strict flatness) is the solvency check, and its failure reverts every transfer in the group. Use `loggedAssert` with a named error, not a raw underflow, so failures are debuggable. One consequence follows. Real transfers cap a flash loan at what the pool account actually holds. Debt beyond real holdings can exist only as internal claim balances (P9), never as tokens.

### Five encodings fit the AVM

The table compares encodings for one ledger entry. It is reasoning from the opcode rules. No source measured opcode costs.

| Encoding | Bytes | Add | Flat test | Assessment |
|---|---|---|---|---|
| **Credit and debit columns** (two uint64) | 16 | Branch-free: `credit += x` or `debit += x` | `credit == debit` | **Recommended for the session ledger.** No sign logic and no underflow path. Columns only grow, so cap per-session amounts against overflow. Matches double-entry bookkeeping. |
| **Magnitude plus sign** (`SignedDelta`) | 9 | Branches in `addSigned` | `mag == 0` | **Keep for persistent pool reserves**, where it is already in audited code. Must normalize `neg = false` at zero, or the counter breaks. |
| Offset (excess 2^63) | 8 | Needs care to avoid intermediate overflow | `x == 2^63` | Compact but halves range; error-prone in PuyaTs. |
| Big-integer offset (`biguint`) | 16 to 32 | `b+` and `b-` | Compare to offset | Wide range, higher opcode cost, still no sign. |
| Net per asset only (Uniswap style) | Small | One signed value | Nonzero counter | Enough for pools. Not enough for margin, where an account ends with debt in one asset and collateral in another. |

### Storage without transient storage

The AVM has no transient, auto-cleared storage. The options are final scratch slots read with `gloads` (earlier calls to later calls only, top level only), logs read through `gtxn`, global state (64 entries, key plus value at most 128 bytes), and boxes ([AVM docs](https://dev.algorand.co/concepts/smart-contracts/avm/); [consensus.go](https://raw.githubusercontent.com/algorand/go-algorand/master/config/consensus.go)). A box created at `open` and deleted at `settle` costs MBR of 2,500 plus 400 microAlgo per byte of key and value, and the delete refunds the app account, not the payer.

The better design, which is an inference from these rules, is **one persistent, pre-funded session box** that settle resets to zero. Groups run one after another in a block, so one box serves every session. A failed group leaves no trace by atomicity. A sizing example (my arithmetic): a 32-byte account, an 8-byte asset ID, and 16 bytes of columns give 56 bytes per entry, so 16 entries fit in 896 bytes, inside the 2,048 bytes of box I/O that one box reference buys ([consensus.go](https://raw.githubusercontent.com/algorand/go-algorand/master/config/consensus.go)). The nonzero counter makes the final flat test one comparison, and the touched-set cap bounds the per-account work, as the EVC cap of 10 does on Ethereum.

### Five session rules close the gaps

These rules come from the precedents and from the marginfi bug. Do the following:

1. In `open`, assert with `gtxn` that the last group transaction is a kernel `settle` call at the same group level. The opcode docs mark `gload` and `gaid` as "T < GroupIndex" only, and give no such limit for `gtxn`. Confirm later-transaction reads with one LocalNet test ([AVM opcodes](https://dev.algorand.co/reference/algorand-teal/opcodes/)).
2. Reject a second `open` while the session flag is set (marginfi `ACCOUNT_IN_FLASHLOAN`).
3. Reject or isolate sessions that an outside app starts in an inner group, because inner groups see only their own transactions. Check `Global.callerApplicationId`.
4. Credit an account only from a measured balance increase (P3). Never from an amount a module declares.
5. While a session is open, block every path that moves positions or authority out of a touched account. In September 2025, marginfi's `transfer_to_new_account` did not check for an active flash loan. An attacker could borrow on account A, move the liabilities to account B, and close the flash loan on an empty A. marginfi held over $160M in deposits, and no funds were lost ([Asymmetric Research](https://asymmetric.com/threat-contained-marginfi-flash-loan-vulnerability/); [fix commit](https://github.com/0dotxyz/marginfi-v2/commit/67ab029e9564d73a4f4b84b1a7ea035cdd1d7c11)).

## The whole wallet cannot back margin under today's ARC-58 code

The user's second concern holds up when checked against the code. The assumption "positions stay in the user's wallet and the whole wallet backs margin" rests on four hidden claims. The settle check enforces solvency. The kernel can liquidate. Wallet value is knowable. No other lender counts the same assets. **Each claim fails under the current wallet contract.** Settle checks only the group it runs in. Liquidation needs signing authority the owner cannot revoke. Wallet value includes assets an issuer can freeze or claw back. Nothing stops a second protocol from counting the same balance.

### The admin can remove any lien in a later group

The local wallet code shows five escape hatches. `arc58_rekeyTo(address, flash)` is admin-only and sends an inner payment with `rekeyTo: address`. With `flash = false` it never requires a rekey back (line 1005). `update(version)` allows `UpdateApplication` by the admin, or by the factory when updates are allowed, so new code can drop any lien logic (line 849). `arc58_removePlugin` requires only admin or the revocation app, and never checks for open debt (line 1323). `arc58_pluginChangeAdmin` lets a plugin with the admin flag set a new admin (line 962). `arc58_toggleEscrowLock` and `arc58_reclaim` are both admin-only, and admin `arc58_reclaim` calls `reclaim(escrow, reclaims, true)` without reading the lock. So the admin can drain and close a "locked" escrow. Only plugin reclaims honor the lock (lines 1430 to 1480) ([local wallet code](../../arc58/account/contract.algo.ts)).

The wallet does enforce one thing well. During a plugin rekey window, `assertValidGroup` walks later transactions and requires `arc58_verifyAuthAddress` before the group ends. It also requires every app call in the window to target the same plugin app, at version 0, with the wallet app ID as the first argument ([local wallet code](../../arc58/account/contract.algo.ts), lines 535 to 575). That protects a session. It does not protect the next group.

### Eleven risks, ranked

| # | Risk | Evidence | Severity | Fix |
|---|---|---|---|---|
| 1 | **Collateral leaves between groups** | Any admin send, reclaim, or rekey outside a kernel group runs no health check | Critical | Margin lives in an escrow only the kernel can move |
| 2 | **Rekey, app update, or admin change** | `arc58_rekeyTo`, `update`, `arc58_changeAdmin`; same class as the marginfi transfer bug | Critical | Kernel custody of the margin escrow, or a debt-aware lien in the wallet |
| 3 | **No forced access for liquidation** | `arc58_removePlugin` revokes the kernel grant at any time | Critical | Forced-action right (P7) that the owner cannot revoke while debt exists |
| 4 | **Issuer freeze and clawback** | An ASA clawback "can reclaim holdings of the asset from any account" ([transaction reference](https://dev.algorand.co/concepts/transactions/reference)); USDC on Algorand is expected to carry both roles (not read on chain) | High | Collateral allowlist; haircut or exclude assets with unknown clawback; reconcile (P11) |
| 5 | **Opt-out and receiver opt-in** | The owner can close an ASA holding; a liquidator must be opted in to receive | High | Pre-opt-in the margin escrow and liquidation receivers |
| 6 | **Malicious or admin-flag plugins** | An admin-flag plugin can change the admin; a new malicious plugin is also version 0 | High | Lien binds the account, not the admin; kernel accepts only cooperating modules |
| 7 | **Heterogeneous valuation** | LP and receipt tokens priced from spot can move inside the same group | High | Allowlisted assets with manipulation-resistant valuators (P8) |
| 8 | **Cross-protocol double pledging** | Two lenders can each count the full wallet balance | High | One controller per margin account (P6); count only assets the kernel custodies |
| 9 | **Dust griefing** | Many small holdings raise settle cost; the EVC caps deferred sets at 10 | Medium | Cap touched accounts and assets per session |
| 10 | **Recovery conflicts** | Social recovery through `arc58_pluginChangeAdmin` is legitimate but must not free collateral | Medium | Lien binds the margin escrow, independent of who is admin |
| 11 | **Liquidation races** | First-come liquidations invite racing; Algorand ordering behavior was not researched | Medium | Bonus cap and partial liquidation |

### What the assumption gets right

The concern applies only to positions that carry debt past the end of a group. A swap, an LP deposit, a vault deposit, or a flash loan that ends flat needs no lien at all. Settle proves the account is whole before the group commits, and there is nothing left to enforce later. So **LP shares, vault shares, LSTs, and spot balances can stay in the user's wallet**. This covers the whole first build stage. The risk begins the moment a module lets an account end a session with debt.

### Two production designs show the fix

Every verified production precedent puts margin either in an account the protocol controls or in cooperating vaults under a single controller. None lets an unrestricted, owner-upgradable personal wallet back debt directly. Gearbox V3 gives each borrower a credit account. The user drives it only through `multicall`, external calls go through allowlisted adapters, a full collateral check runs at the end, and anyone can call `liquidateCreditAccount` once value falls below debt ([CreditFacadeV3.sol](https://github.com/Gearbox-protocol/core-v3/blob/main/contracts/credit/CreditFacadeV3.sol)). Euler's EVC lets the user own the account, but collateral counts only inside vaults that report every outflow. An account has at most one controller, only the controller can disable itself, and the controller can seize collateral with `controlCollateral` ([EVC whitepaper](https://github.com/euler-xyz/ethereum-vault-connector/blob/master/docs/whitepaper.md)).

ARC-58 already has the Gearbox shape: a named escrow, which is a separate Algorand account the wallet controls. The recommended design has two options. **Option A (no wallet change):** the margin escrow is rekeyed to the kernel, not to the wallet. Deposits in are measured credit. Withdrawals out run the controller's health check. Liquidation runs without the owner. The user keeps a portfolio margin account inside the escrow, which covers cross-margin across modules without pledging the whole wallet. **Option B (wallet change):** the wallet's `arc58_removePlugin`, `arc58_removeAllowances`, `arc58_reclaim`, `arc58_toggleEscrowLock`, `arc58_rekeyTo`, `update`, and admin-plugin `arc58_pluginChangeAdmin` refuse to touch the margin escrow or the kernel grant while the kernel reports debt. Only the kernel releases the lien, like EVC `disableController`. Option B changes an existing contract. Under the project rules it needs the user's explicit approval. Option A should ship first, because it needs no contract change and matches Gearbox.

Reconcile (P11) must classify ALGO growth as yield, not as a donation. |

Two constraints come from the wallet, not the protocol, and they matter most. First, **the ARC-58 version-0 rule makes the kernel immutable in practice**. During a wallet rekey window, every app call must target the plugin at app version 0 ([local wallet code](../../arc58/account/contract.algo.ts)). If the kernel is that plugin, any update breaks every wallet flow. So version the kernel by deploying new app IDs, and keep upgrades in modules pinned by `RejectVersion`. Second, **two wallet rekey windows cannot overlap in one group**, by my reading of the same code. Inside wallet A's window, every app call must pass wallet A's app ID as its first argument, so wallet B's rekey call fails there. A group that settles a maker wallet against a taker wallet must therefore run the windows in sequence: rekey A, act, verify A, rekey B, act, verify B, settle. Each window costs at least three transactions, so a 16-transaction group holds about four wallet windows. This is an inference from the code and needs a LocalNet test.

The ecosystem adds three more constraints. **Oracles are the weakest link.** No native Chainlink or Pyth price feed on Algorand is confirmed. Folks Feed Oracle is a beta app with prices in global state ([Folks Feed SDK](https://github.com/Folks-Feed-Oracle/folks-feed-python-sdk)). Gora has no primary documentation in this survey, and Tellor's Algorand contracts are legacy ([Algorand developer article](https://developer.algorand.org/articles/teal-algo-oracle-algorand-layer-1)). Folks runs Chainlink, Pyth, and DIA on its hub chain, not on Algorand ([Folks xApp docs](https://docs.xapp.folks.finance/technical-details/oracle)). **Liquidity is thin.** Chain-wide DEX volume was about $199k in 24 hours on 4 Nov 2026 ([DefiLlama DEX overview](https://api.llama.fi/overview/dexs/algorand)), so liquidation design must assume high slippage outside ALGO, USDC, and LSTs. **USDC is the only usable stablecoin.** USDT supply is about $0.84M, too thin for liquidations ([DefiLlama stablecoins](https://stablecoins.llama.fi/stablecoins?includePrices=false)).

## Ship the flatness kernel first and the solvency kernel second

The build order follows dependency and Algorand demand. Algorand's largest non-bridge TVL is RWA (Lofty $101.1M), staking pools (Reti $75.5M), and liquid staking (xALGO $25.7M). Lending is $23.6M at Folks, and trading pools are small ([DefiLlama](https://api.llama.fi/protocols)). The stages below each end in a verifiable state.

**Stage 0: kernel core with flat-only settle.** Build P1 to P5 in a new immutable app. Reuse the Plugin DEX custody guard, measured-delta snapshot, and `SignedDelta` code. Use credit and debit columns in one pre-funded session box. Settle accepts only flat or invariant-preserving accounts in this stage. Before any module, run LocalNet tests for later-transaction `gtxn` reads, `EnforceAuthAddrSenderDiff` on rekey back, minimum-balance timing inside a group, and two sequential wallet windows in one group.

**Stage 1: spot, routing, and flash loans on flat sessions.** Plugin DEX pools become kernel modules behind P15. Add P16 (exact quotes, per-leg budgets, discovery) and P17 (fees with a referral slot), and integrate Haystack Router as the first flow source. Flash loans and flash swaps come free from P2 and P5. No lien is needed, so positions stay in user wallets.

**Stage 2: shared services and yield.** Build P8 as a module: a push feed (Folks Feed or Gora, after their coverage is verified) bounded by a kernel-pool TWAP, with staleness in rounds and a deviation check. Build P9, P10 (including withdraw-only mode), and P11. Products: ERC-4626-shaped vaults, LST receipt pricing, ALGO pool accounts that earn consensus rewards, and a USDC savings wrapper that keeps the payment stablecoin non-yielding, as GENIUS and MiCA require ([CRS IF13174](https://www.congress.gov/crs-product/IF13174); [Legal500](https://www.legal500.com/intelligence/united-states/technology/why-does-mica-and-the-genius-act-ban-stablecoin-interest)).

**Stage 3: the solvency kernel.** Add P6, P7, and P12 with Option A margin escrows in kernel custody. Ship isolated lending markets through the P22 factory, with ALGO, xALGO, and USDC collateral, issuer-risk haircuts, and liquidation routed through Haystack and Tinyman. Decide here whether to request the Option B wallet change. That decision needs the user's explicit approval.

**Stage 4: signed orders and delegation.** Add P13 and P14 on ARC-58 execution keys and allowances. This unlocks limit, stop, DCA, RFQ, and Dutch-auction orders. Add P21 for per-round batch clearing, which suits 2.8-second rounds better than a latency race.

**Stage 5: stablecoins, fixed rate, and RWAs.** Add P18 (capped minting, PSM, PT and YT split), P19 (maturity, epochs, async queues), and P20 (redemption order, price bands). RWA support needs ARC-20 transfer adapters, allowlisted liquidators through gates, and async redemption.

**Stage 6: derivatives.** Start with oracle-priced pool perps using two-step keeper execution, or a per-round batch book. Add RFQ options and outcome tokens with a bonded resolver. Start this stage only after P8 accepts signed pull reports verified in the group. A perps engine on an unverified price feed repeats the Lighter trust gap that L2Beat flagged, where Stork signatures are not verified on chain ([L2Beat](https://l2beat.com/publications/exchange-risk-and-how-lighter-escapes-it)).

The deferred items (a full order book, cross-chain intake, restaking, vote escrow) wait until a stage above creates demand for them.

## Conclusion

The survey changes the framing of the kernel. It is not one solvency engine. It is **two kernels that share a ledger**. The flatness kernel needs no oracle, no lien, and no wallet change, and it already carries spot, routing, flash loans, vaults, and LST flows. The solvency kernel needs a trustworthy price, a lien the owner cannot lift, and a liquidation right, and on Algorand today the blockers are an oracle gap and a wallet-contract decision, not code. That split also answers both user challenges at once. The uint64 limit disappears once debt is a ledger column rather than a balance. The wallet-margin risk disappears once debt lives only in a kernel-held escrow, while ordinary positions stay where users want them.

Two Algorand-specific findings deserve weight beyond this survey. The ARC-58 version-0 rule and the 16,384-byte cap together force an immutable kernel versioned by new app IDs, which removes the Drift-class risk of an upgradable core by construction. And because the scarce resources are references, group slots, and log bytes rather than opcodes, the kernel must cap touched accounts per session, as the EVC caps its deferred sets at 10. The open items to verify before Stage 0 code are the later-transaction `gtxn` read, the rekey-back rule under `EnforceAuthAddrSenderDiff`, minimum-balance timing inside a group, sequential wallet windows, the extra-page MBR formula, USDC's on-chain freeze and clawback addresses, and real coverage of the Folks Feed and Gora oracles.
