Your two challenges, checked

Both challenges hold on the facts. The first one does not block the design. The second one changes it.

1. "Within a contract an underflow will cause a panic"

This is correct. The AVM - opcode fails when B > A, and b- also fails on underflow. The AVM has no signed integer type. But no production system in the survey stores a negative token balance. Each one stores a ledger entry and moves real tokens only when someone pays.

  • Uniswap v4 keeps one signed int256 per (caller, currency) in transient storage. unlock reverts with CurrencyNotSettled unless a nonzero-delta counter is zero.
  • Balancer v3 uses the same design with the opposite sign. settle credits the live balance minus booked reserves, capped by a caller hint.
  • Euler v2 EVC does not net deltas. It defers health checks to the end of the batch, in a set capped at 10 accounts.
  • Sui uses a "hot potato" receipt with no abilities, so the VM refuses to end the transaction until the loan is repaid.
  • Plugin DEX already does this on the AVM. math.ts defines SignedDelta {mag, neg} and bans raw subtraction on delta paths. applySigned asserts value >= mag before it subtracts.
The abort is the enforcement. Inside the session, code only adds to two ledger columns, credit and debit. At settle, one named assert per account (credit >= debit) is the solvency check. If it fails, the whole group reverts, and every transfer in it is undone. A real flash loan is capped at what the pool actually holds, because a transfer above the balance fails.

The AVM has no transient storage. The report recommends one persistent, pre-funded session box that settle resets to zero. Groups run one at a time, so one box serves every session, and a failed group leaves no trace. 16 entries of 56 bytes use 896 bytes, inside the 2,048 bytes of I/O one box reference buys. That sizing is arithmetic, not a measurement.

Five session rules

  1. In open, use gtxn to assert that the last transaction in the group is a kernel settle call. The docs limit gload and gaid to earlier transactions, but not gtxn. Confirm with a LocalNet test.
  2. Reject a second open while a session is open.
  3. Reject or isolate sessions that start in an inner group, because an inner group sees only its own transactions.
  4. Credit an account only from a measured balance increase, never from an amount a module declares.
  5. While a session is open, block every path that moves positions or authority out of a touched account. In Sept 2025, marginfi's transfer_to_new_account let a borrower move liabilities to a new account during a flash loan, so the check passed on an empty account. It held over $160M; nothing was lost.

2. "The whole wallet backs margin creates risk"

This is correct, and the wallet code confirms it. Settle checks only the group it runs in. In any later group, the ARC-58 admin can remove a lien in five ways. Line numbers are in arc58/account/contract.algo.ts.

  • arc58_rekeyTo(addr, false) rekeys the account away with no rekey-back (about line 1005).
  • update replaces the app code (about line 849).
  • arc58_removePlugin removes any plugin with no debt check (about line 1323).
  • arc58_pluginChangeAdmin lets an admin-flag plugin set a new admin (about line 962).
  • Admin arc58_reclaim ignores the escrow lock, so the admin can drain a "locked" escrow (lines 1430–1480).

What the wallet does enforce well: during a plugin rekey window, assertValidGroup requires every call to target the same plugin at app version 0, and requires arc58_verifyAuthAddress before the group ends. That protects one session. It does not protect the next group.

What the idea gets right. The risk exists only for positions that carry debt past the end of a group. A swap, an LP deposit, a vault deposit, or a flash loan that ends flat needs no lien. So spot balances, LP shares, vault shares, and LSTs can stay in the user's wallet. That covers the first three build stages.

Option A (no wallet change, ship first). Each margin account is an ARC-58 escrow rekeyed to the kernel. Deposits in count as measured credit. Withdrawals run the controller's health check. Anyone can liquidate without the owner. This is the Gearbox credit-account shape. The user still gets cross-margin across modules inside that escrow.

Option B (wallet change). The wallet's rekey, update, remove-plugin, reclaim, lock-toggle, and admin-change paths refuse to touch the margin escrow while the kernel reports debt. Only the kernel releases the lien, like Euler's disableController. This changes an existing contract, so it needs your explicit approval.

Algorand limits that shape the kernel

Two wallet rules matter most. First, the ARC-58 version-0 rule makes the kernel immutable in practice. A new kernel version needs a new app ID. Second, by the report's reading of the wallet code, two wallet rekey windows cannot overlap in one group. A group that settles a maker wallet against a taker wallet runs the windows one after the other, so about four wallet windows fit in 16 transactions. That is an inference and needs a LocalNet test.

The ecosystem adds three more limits. No native Chainlink or Pyth feed on Algorand is confirmed. Chain DEX volume was about $11.9M over 30 days (DefiLlama, 4 Nov 2026). USDC ($112.2M) is the only stablecoin deep enough for liquidations.

Ship the flatness kernel first, because it needs no oracle, no lien, and no wallet change. Then build the solvency kernel.
